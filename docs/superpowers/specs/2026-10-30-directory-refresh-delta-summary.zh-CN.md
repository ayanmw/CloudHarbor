# 目录刷新变更摘要设计

## 目的

刷新运行历史目前记录某目录刷新后是否变化，但用户无法从历史直接判断变化规模。本版本为每个完整发布的目录增加新增、移除和元数据变化计数，帮助核对本地缓存如何跟随远端列表更新。

## 目标与非目标

- 对刷新前已有完整本地目录清单的目录，按稳定 `fs_id` 对比旧清单与本次完整百度列表，分别统计新增、移除和属性变化条目。
- 将计数和既有本机记录 UTC、百度列表观测 UTC、`directory_changed` 一起写入 SQLite append-only 刷新事件；网页历史与既有 JSON 证据导出显示这些计数。
- 只在完整目录发布事务中生成摘要。读取失败、暂停、部分分页、结果未知不会发布计数或更改既有完整快照。
- 初次扫描或刷新前缓存状态不是 `complete` 时，计数为未知/null；不得将不完整缓存误报为所有条目新增或删除。
- 不保存每个变更文件的完整副本，不新增百度请求、远端写操作、后台任务或保留策略。

## 分类规则

- **新增**：本次远端直系条目的 `fs_id` 不在刷新前完整本地直系条目中。
- **移除**：刷新前完整本地直系条目的 `fs_id` 不在本次远端直系条目中。
- **变化**：`fs_id` 两边都存在，但 `path`、`name`、目录类型、大小、provider mtime 或 content MD5 任一不同。
- 一个 `fs_id` 只归入以上一个类别；目录移动跨父目录时，旧父目录计为移除，新父目录计为新增；同父目录改名计为变化。
- 刷新前覆盖完整时三项计数始终有值，包括 0；覆盖不完整时三项均为 null。

## 实现方案

1. **刷新事件表增加 nullable 计数列（采用）**：单个目录事件行保存三个计数，不新增逐文件事件行；数据库增长随刷新目录数增长。旧 schema 迁移后既有事件的新增列为 null。
2. **每项变更追加事件行**：明细最细，但全盘每轮可能产生数千条新事件，增加存储、查询和导出负担，不符合只补关键事件的既定偏好。
3. **把计数塞入自由格式 evidence JSON**：无需迁移，但失去 SQLite 列约束与稳定字段读取，和现有结构化事件接口风格不一致。

## 持久化和兼容约束

- SQLite schema 20→21；新增 nullable、非负整数列，沿用现有 `store_meta`、manifest 恢复流程和 append-only trigger。
- 迁移在单个事务内完成，schema_version 最后更新；若 SQLite 已提交但 manifest 尚未原子发布，重启验证新列后补齐 manifest。
- 旧事件读取时计数保持 null；不回填推测值。
- 库存发布、目录状态、刷新游标和事件保持同一 SQLite 事务。事务失败时全部回滚。

## 验收

- Store 覆盖完整旧缓存下新增/移除/变化/不变分类、相同 `fs_id` 元数据变化、跨父目录视角、无完整旧缓存时 null、事件与库存同事务回滚。
- schema 20→21 迁移保留旧历史且新字段为 null；manifest 落后恢复、重开读取及 append-only 约束通过。
- API 与既有事件导出包含计数且不泄露账号指纹；UI 在历史时间线上展示计数，未知时显示“无完整旧缓存基线”。
- 全仓 Go 测试、vet、WebUI/userscript、Windows AMD64/Linux AMD64/Linux ARM64 三平台包、ZIP 来源快照和私有数据检查通过。
- 仅使用本机 SQLite/mock，不访问真实百度账号或 NAS/SMB。
