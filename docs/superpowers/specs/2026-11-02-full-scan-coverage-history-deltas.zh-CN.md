# 全盘扫描覆盖历史变化对比设计

## 意图

在全盘扫描历史中解释当前完成轮相对紧邻上一轮完成扫描的覆盖变化，帮助用户判断缓存完整度是在改善还是恶化。所有值来自当时 SQLite 历史快照，严格保留两轮的本机观察 UTC；不读取当前缓存补写过去，也不调用百度 API。

## 目标

- 每条完成扫描历史可显示与其紧邻的上一条完成扫描的覆盖摘要对比。
- 比较覆盖状态、未完整目录数，以及九项覆盖原因计数；差值采用“当前轮减上一轮”，正数表示问题计数增加。
- 对比证据明确列出当前轮和上一轮的 run ID、sequence、观察 UTC 和原始快照。
- 仅当两个相邻完成轮都记录所需字段时计算差值。遇到旧历史 NULL 时标为证据不足，不跳过缺口去找更早的记录。
- 历史列表、单轮 API 及单轮 JSON 证据导出遵循相同定义，不泄漏账号指纹。

## 非目标

- 不新增 SQLite 表或回填历史；不将当前缓存覆盖、generation 或时间用于重建过去。
- 不比较失败/暂停/运行中的扫描轮，也不跨过缺失快照继续找更早记录。
- 不增加百度请求、后台扫描、筛选器或远端操作。

## 方案

1. 在 SQLite 查询结果中按账号、完成状态和不可变 sequence 找到紧邻前一条完成记录，再由 Go 计算差值。推荐此方案：业务规则清楚，NULL 和相邻关系可审计，兼容当前 SQLite 版本；代价是历史页有少量本地查询。
2. 使用 SQL 窗口函数批量生成比较。减少查询数，但需处理筛选分页前后窗口范围、NULL 快照以及现有 SQLite 兼容性，增加查询复杂度。

采用方案 1。历史规模和页大小有限，减少少量本地 SQLite 读取不值得引入复杂窗口查询。

## 证据与显示规则

- 前一轮定义：同一账号下 sequence 最大且小于当前轮、status 为 `complete` 的扫描轮，不受当前页面筛选条件影响。
- 如果没有前一轮，比较状态为 `no_previous_run`。
- 如果前一轮缺覆盖快照/观察时间/未完整目录数，比较状态为 `previous_snapshot_unrecorded`；当前轮缺这些字段时为 `current_snapshot_unrecorded`。
- 原因差值仅当两轮均有原因 JSON 时提供；否则原始快照仍可显示，原因差值状态为 `reasons_unrecorded`。
- 完整比较时覆盖原因差值包括 scanning、stale、unknown、failed、missing status、orphan status、parent incomplete、path mismatch、missing root 九类。原因计数可重叠。
- 完成顺序按 SQLite sequence 判定；观察 UTC 展示为各自记录的云端缓存观察时刻，不暗示远端原子快照。

## 验收

- 覆盖状态、未完整目录数、原因计数变化均使用当前减前一轮，且支持负值。
- 相邻轮缺快照时不越过查找更早轮；任一旧 NULL 不变成零。
- 账号隔离、同时间 sequence 稳定顺序、首轮无前序、原因为 NULL、导出 DTO 脱敏均有回归。
- API 与 UI 标出两轮 UTC；单轮导出含同样比较证据；现有历史行为与筛选分页不变。
- 不触发百度请求。

## 实现边界

沿用现有 Go taskstore/API/UI 和 SQLite 只读历史路径，新增轻量比较 DTO，不新增依赖或迁移。设计执行按用户对本项目的持续实现授权在主目录内完成；NAS/SMB、ARM64 原生设备和真实百度写操作不在验收范围。
