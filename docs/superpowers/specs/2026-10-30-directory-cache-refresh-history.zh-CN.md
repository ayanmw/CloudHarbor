# 目录缓存刷新历史

## 意图

让用户在长时间或中断的网盘目录缓存刷新后，查看发生过的关键状态变化和已核对目录，而不只看到 SQLite 中最近一次运行快照。记录需在重启后保留，并分别标明本机记录时间与百度列表观测时间。

## 当前行为

- `cloud_inventory_refresh_state` 只保存一个账号最近的刷新状态和检查点。
- 刷新可以跨重启暂停和续跑，但新运行替换状态后，之前运行的阶段信息和目录完成顺序无法在页面查看。
- 每个目录的缓存观测时间独立保存在目录表中；这些数据不是刷新运行历史，也不说明刷新何时暂停、失败或恢复。

## 目标

- 在 SQLite 中追加保存刷新生命周期关键事件：开始、重启恢复、暂停、失败、完成，以及每个目录完成完整远端读取并发布缓存。
- 每条事件记录账号指纹、稳定 run ID、单调序号、事件类型、当前目录、进度快照、本机 UTC 记录时间；目录完成事件另外记录网盘目录列表响应被本机完整读取时的 UTC 时间及该目录是否与旧缓存有变化。此观测时间由本机时钟产生，不是百度服务器时间；事件记录时间表示 SQLite 写入事件时的本机 UTC。
- 事件和对应刷新状态/缓存发布使用同一 SQLite 事务；失败不得出现状态已改变但事件缺失，或事件声称发布成功但缓存事务回滚。
- 通过管理认证保护的只读 API 按账号和 run ID 分页读取；按需访问，不引起网盘请求。
- 在目录缓存刷新面板内提供可折叠的本地历史时间线，默认不请求；显示两类 UTC 时间、运行 ID、事件类型、目录及进度，并安全转义内容。
- schema 从 18 原子迁移到 19；已有运行状态保持不变，历史从升级后开始记录，不伪造旧事件。

## 非目标

- 不逐页或逐文件记录事件，不重复存储每个缓存项。
- 不修改扫描调度、限流、暂停/续跑、远端 API 请求和缓存提交语义。
- 不为过去运行合成时间或 provider 观测证据。
- 不提供修改、删除、重放或恢复历史记录的入口。

## 方案与取舍

1. **SQLite append-only 事件表（采用）**：在现有刷新状态与发布事务内追加关键事件；可跨进程重启、账号隔离并分页读取，数据增长按生命周期和已完成目录数计算。
2. **仅延长当前状态表**：可保留更多最近字段，但会失去多次运行与每目录完成顺序，无法满足可审计的历史视图。
3. **从应用日志解析历史**：无需数据库迁移，但日志轮转、格式变化和时间/账号关联会使证据不完整，也无法提供可靠分页。

采用方案 1。事件只覆盖状态转换与目录发布，不覆盖每个分页请求，以控制存储增长。

## 行为规则

- 同一 SQLite 事务写入事件与其所描述的状态变化；目录事件必须与正式缓存发布同事务。
- 每次新 run 追加 `started`；已存在的运行检查点重新启动追加 `resumed`；用户暂停追加 `paused`；刷新错误追加 `failed`；队列排空追加 `completed`。
- 每个目录完整提交后追加 `directory_published`，记录远端观测时间、缓存是否变化、已处理页数/条目数和剩余目录数。
- 页面按用户点击读取一个 run 的事件，最新事件优先分页；加载更早事件使用稳定的 sequence 游标。切换 run 或关闭详情时忽略迟到响应。
- 历史读取错误保留现有条件与重试入口；页面文案指明这是本机 SQLite 记录，不能据此认定百度当前状态。

## 验收

- Store 测试覆盖追加、顺序游标、账号/run 隔离、跨关闭重开、事件与状态/缓存事务原子性、失败回滚及 v18→v19 迁移恢复。
- Downloader/API 测试覆盖新建、续跑、暂停、失败、完成及目录发布事件；管理认证 GET 不访问百度 API，参数边界明确。
- WebUI 测试覆盖默认不请求、按需加载、分页、UTC 时间区分、路径转义、迟到响应、失败重试。
- 全仓 Go 测试/vet、WebUI/userscript、Windows AMD64/Linux AMD64/Linux ARM64 构建、ZIP 清单/源码快照/私有运行数据检查全部通过。
- 仅本地与模拟服务验收；不触碰真实百度账号或 NAS/SMB。
