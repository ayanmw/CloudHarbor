# 任务历史 SQLite 存储改造设计

## 背景与决定

Windows 合成队列基准显示，100,000 条任务在当前环境中完整恢复约需 12.9–17.7 秒；这与逐条文件读取路径的耗时同量级。现有 v1 格式为每条任务一个 JSON 文件，启动需要枚举、打开、校验并解码大量小文件。

用户已明确允许落地存储改造并指定 SQLite，同时要求重启后记录安全，严格区分过去/未来、本地/线上状态，并保留时间等证据。本文据此以事务型 SQLite 数据库替代此前提出的追加日志文件方案。

本文先建立可审阅的实现边界。NAS/SMB 的锁与刷盘语义不能由本机测试代替；若目标部署把数据库放在网络文件系统，必须通过目标文件系统实测，不能仅凭 SQLite 事务语义声称断电安全。

## 目标与非目标

- 当前任务状态与对应状态变化证据必须在同一 SQLite 事务中提交，避免当前态和历史证据分叉。
- 崩溃或重启后，要么恢复到最后一次已确认提交的完整状态，要么明确失败关闭；不得跳过损坏记录、猜测云端操作成功或自动重发可能已发送的云端修改。
- 将不可变的过去事件与当前投影、未来计划分别表示，记录时间、观察来源和证据类型。
- 无损迁移 v1 中现有任务记录；旧数据没有保存的历史转换细节必须标明未知，绝不伪造。
- 保持任务生命周期、重试策略、下载/源后处理规则、任务查询及历史保留语义。
- 不把入队 `sending/unknown` 日志、OAuth 凭证、管理员密钥或下载模式设置合并进任务数据库；原有独立存储保持分离。
- 不承诺 SQLite 在任意 NAS、SMB、NFS 或容器卷上的持久性。目标文件系统未通过验证门槛时，不宣称已验证适用于该 NAS。

## 数据模型

采用两个逻辑层：`jobs` 保存每个任务的当前状态投影；`job_events` 追加记录状态变化证据。每次状态变更必须在一个事务内追加事件并更新 `jobs`。当前列表仍从 `jobs` 提供；诊断可按序读取事件。迁移期间可继续把完整 `queueJob` JSON 放在 `jobs.payload_json`，另用有约束的列保存常用索引字段。

建议的关键表：

- `store_meta`：格式版本、队列范围、数据库生成 ID、迁移来源/时间及兼容信息。
- `jobs`：`fs_id` 主键、完整任务 JSON、当前状态、下载模式、源操作状态、最后事件序号、首次记录时间、最近更新时间、未来 `next_attempt_at`。
- `job_events`：单调递增序号、`fs_id`、事件类型、前后状态、动作/尝试 ID、来源类别、证据等级、本机记录时间、已知发生时间、云端观察时间（如适用）、进程启动实例 ID、脱敏响应/错误摘要和必要状态快照。

事件表只追加；过去事件不能被改写为新状态。当前态可以随新事件更新。不能把“计划重试”当作“已经重试”，也不能把本地任务状态当作云端现状。

## 时间与证据语义

- `recorded_at_utc` 是本机写事件时观测到的 UTC 墙上时钟，采用 Unix 微秒整数；它不是百度服务器时间。系统时钟可能回拨或漂移，因此事实顺序以数据库 `seq` 为准，不能只按时间戳排序。
- `occurred_at_utc` 仅在事件的实际发生时点有证据时填写；未知则为空，不从相邻任务时间推算。
- `cloud_observed_at_utc` 是本机收到某次成功云端元数据读取结果的时间。它表示“本机此时观察到这些值”，不表示云端对象在此时创建、修改或完成。
- 百度返回的 `mtime` 等提供方时间单独保存为 `provider_mtime`，按 API 原始语义解释；不得与本机观察时间混用，也不得据此伪造本地操作时间。
- `next_attempt_at_utc` 是未来最早允许重试的计划时间。只有到期并且实际开始尝试后，才追加新的 `attempt_started` 事件。时钟跳变时，事件序号仍保持事实顺序；调度器沿用现有重试资格逻辑。
- 每次进程启动生成新的随机 `run_id`，每次可能产生线上副作用的操作使用唯一 `operation_id`/`attempt_id`。这些 ID 连接准备、发送、响应和恢复证据，不能复用旧尝试 ID。
- v1 记录只迁移实际保存的 `Created`、`Updated` 和状态快照，并写入一条 `legacy_import` 事件，记录迁移时刻、旧格式和原时间字段。旧数据未保存的中间状态、线上响应时间和来源明确标为未知，不补造。
- 证据摘要不得包含 Access Token、管理员口令、请求认证头、带凭证 URL 或可重放请求的秘密。只保存审核所需的操作类型、脱敏错误分类、HTTP/业务码、返回字段完整性及同步确认情况。

## 本地状态与线上事实的边界

- 本地事件来源至少区分 `scheduler`、`user_action`、`local_recovery`、`cloud_observation`、`cloud_response` 和 `migration`。来源说明证据从何而来，不代表推测。
- `pending`、`downloading`、`done`、`retry_wait` 等是本地调度器状态，只说明本程序记录的流程，不直接宣称百度云端对象当前存在、已改名、已删除或已完成。
- 云端对象信息只有在成功读取 API 响应后，才能作为带 `cloud_observed_at_utc` 的线上观察写入。源项操作只有收到现有严格同步完成凭据后，才能记录为 `cloud_response/confirmed`。
- 发请求前先在事务中写入 `source_operation_sending` 事件与当前 `sending` 投影，并确认提交成功，之后才允许发 HTTP。若进程在提交后、请求前崩溃，重启将未决操作保守转为 `unknown`，因为无法证明请求未发出。
- 收到明确同步成功后，另开事务记录 `source_operation_confirmed`、接收时间、操作 ID 和脱敏响应摘要，并更新任务为完成。明确拒绝按现有策略记录；超时、断连、异步受理、响应不完整及确认落盘失败均恢复为 `unknown`，不自动重发，也不提供人工解除入口。
- 若已收到响应但确认事务提交失败，磁盘上的旧 `sending` 仍是唯一可证明状态；重启后转为 `unknown`。内存状态不得显示为已确认完成。
- 云端扫描结果与数据库状态冲突时，沿用已验证的身份冲突规则；不得仅凭本地旧记录或陈旧列表覆盖身份、解除隔离或执行线上副作用。

## SQLite 文件与耐久设置

- 数据库放在现有持久化队列状态目录，确保与任务队列处于同一持久卷，并使用仅服务账户可读写的权限。迁移期间保留 v1 文件，直到新库通过关闭、重新打开、完整性与数据等价验证。
- 为保持 Windows、Linux AMD64 和 Linux ARM64 的无 CGO 交叉构建，优先选纯 Go SQLite 驱动。实现时须根据项目最低 Go 版本现场核验具体依赖版本，并验证三平台构建与 race；不能只按当前最新版决定。
- 保留单进程 `writer.lock`；数据库连接池限制为一个写连接，事务串行提交，设置有限 busy timeout。锁冲突必须作为错误上报并停止后续调度，不能丢弃或跳过保存。
- 基线采用回滚日志 `journal_mode=DELETE`、`synchronous=EXTRA` 并启用外键；启动时读取并回验实际 pragma。DELETE 模式用于避开 WAL 要求所有数据库使用者位于同一主机且不支持网络文件系统的限制，但它不能修复错误的 SMB/NFS 锁实现。
- 不通过降低同步级别、异步批量提交或忽略 `SQLITE_BUSY` 换取吞吐。新任务批量登记可在一个事务中提交；每次业务状态变更独立提交，尤其 `sending` 必须在网络请求之前完成并确认耐久提交。
- 每次打开都检查格式版本、队列范围、完整性和所需 pragma。数据库缺失、损坏、范围不符、版本不兼容或同步设置未生效时，失败关闭；不得静默重建空库或回退读取过期文件。

## v1 到 SQLite 的迁移

1. 获取现有单写入者锁，读取并校验 v1 清单和所有任务文件；不改源文件，也不触发云端操作。
2. 在同一目录创建唯一暂存数据库，写入格式/队列范围元数据、任务当前投影和明确标注 `legacy_import` 的事件。可分批处理以限制内存；任何校验失败都停止迁移。
3. 关闭暂存数据库后重新打开，执行完整性、范围、记录数、ID、JSON 和状态校验。逐 ID 核对迁移后当前任务与 v1 记录等价；不伪造历史事件。
4. 数据库内容及目录项可靠落盘后，原子发布最终数据库文件，再原子切换根格式清单到 SQLite 版本并同步目录。清单切换是唯一权威提交点。切换前出错时 v1 仍有效；切换结果不确定时必须关闭存储并失败启动，让下次启动检查实际清单与数据库，同一进程不得切回 v1。
5. 清单指向 SQLite 后，SQLite 成为唯一权威来源。若新库缺失或损坏则失败关闭，不自动从 v1 复制恢复或降级。只有 SQLite 重开并通过等价验证后，才能通过可重试清理删除 v1 文件。
6. 日志与测试指南记录迁移开始/完成时间、旧/新格式、源/目标记录数、数据库大小、校验结果、迁移实例 ID 和失败阶段；不记录秘密。迁移失败时不得启动 scheduler worker 或发送云端请求。

## 崩溃恢复与运维证据

- 故障点覆盖 schema 创建、迁移批次提交、数据库关闭、重开/完整性检查、数据库文件发布、格式清单切换及切换后的 v1 清理。
- 当前任务表与事件表必须原子更新。注入提交失败后重新打开数据库，必须同时看到事务前状态且无该事务事件，或同时看到事务后状态及其事件；不允许只提交一边。
- 模拟 `sending` 提交后但 HTTP 发送前崩溃、请求已发但响应丢失、收到同步成功但确认保存失败、明确拒绝、正常同步成功和进程重启。逐一核对当前态、事件证据及重试资格。
- 时间测试覆盖本机时钟回拨/跳跃：事件序号不回退；线上 `mtime` 不覆盖本机时间；未来 `next_attempt` 不被记录成已发生事件。
- 数据库备份只允许在 SQLite 关闭时进行，或使用受支持的在线备份机制；不得将运行中主库的单文件复制视为一致快照。数据库、回滚日志与目录项作为一个一致性单元管理。
- 启动诊断至少报告格式版本、队列 scope 摘要、记录数、最近提交序号、迁移状态、完整性检查结果、pragma 实际值及本机 UTC 时间；不得暴露凭证。

## 验证与独立预览版门槛

- Windows 与 Go 1.22.2 WSL 上运行迁移、每类状态事务与重启恢复的测试和 race/vet；覆盖完整性错误、约束冲突、锁冲突、提交失败、重复尝试和未知线上结果。
- 使用相同 Go 工具链与夹具，在 Windows 和 WSL ext4 对照 10k/100k 队列：报告中位数、冷/热样本、分配与峰值/保留堆、数据库大小、迁移耗时及迁移峰值磁盘占用。性能结论按环境分别陈述。
- 构建 Windows AMD64、Linux AMD64 和 Linux ARM64；运行 Node UI 测试，确认任务列表与计数契约不变；在 Linux AMD64 包内验证启动与管理认证。
- 在目标 NAS 文件系统单独验收重启/断电或强制终止、单实例锁、回滚日志恢复、完整性检查和目录同步行为。如果该环境锁或刷盘语义不可靠，就明确标注不支持该存储位置；本机测试不替代此门槛。
- 只有 v1 数据无损、故障注入证明事务原子性、未知线上操作不会重发、三平台包验证通过且实际文件系统限制明确后，才发布独立预览包。

## 其他仍待解除的阻塞与验收项

- **百度异步操作完成查询契约仍未证实。** 现有公开资料不能证明 OAuth 应用可查询异步任务的可靠终态。在取得适用的官方契约前，结果不确定的目录继续隔离，不按路径可见性推断完成，也不提供人工放行。
- **真实百度/NAS 端到端尚待用户环境验收。** 本地替身、合成队列和包内冒烟不能证明真实账号的入队、Move、下载、改名/删除、限流恢复或断电恢复表现。
- **目标 NAS/SMB 的 SQLite 锁与刷盘语义待实测。** SQLite 官方文档警告网络文件系统锁实现异常会导致损坏风险；WAL 不支持网络文件系统。设计选 DELETE 回滚日志和 `synchronous=EXTRA`，但这仍需在用户的实际挂载方式、NAS 型号与容器卷上做重启/强制终止验证。
- **浏览器和油猴的实机兼容待验收。** 实际百度 SPA 选择模式、油猴沙箱以及目标浏览器原生 Basic 登录/TLS 反代尚未完整验证；现有页面与 DOM 夹具不能代替实机结果。
- **NAS 长队列与长期运行指标待用户回报。** NAS 启动时延、峰值内存、空闲 CPU、并发/限流、长时间运行和目标浏览器分页体验都需目标环境数据。

其中只有“百度异步完成查询契约”和“目标 NAS 对 SQLite 的锁/刷盘支持”会直接限制相关能力是否能作出安全保证；其余项是发布前/部署后的外部验收，不阻止先实现并验证本地 SQLite 版本。

## 实现阶段待核实事项

- 核对最低 Go 版本后选择并锁定纯 Go SQLite 驱动兼容版本，记录许可证、依赖体积、三平台构建及 race 结果。
- 在真实 NAS/容器挂载上确认 DELETE 日志模式与 `synchronous=EXTRA` 的锁和刷盘表现。PRAGMA 值本身不能证明底层设备兑现同步请求。
- 根据事件增长与磁盘容量测量决定实现细节。用户要求保留历史；若证据表增长超过预期，先报告数据和取舍，不擅自设置裁剪期限。

## 依据

- SQLite 文档说明 WAL 要求所有数据库使用者位于同一主机，且不适用于网络文件系统：[Write-Ahead Logging](https://www.sqlite.org/wal.html)。
- SQLite 锁文档指出网络文件系统锁若不可靠会产生损坏风险，并建议避免在网络文件系统上使用数据库：[File Locking And Concurrency](https://www.sqlite.org/lockingv3.html)。
- SQLite `synchronous=EXTRA` 在 DELETE journal 模式下会在删除回滚日志后同步目录，增加紧接着断电时的提交耐久性：[PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。
