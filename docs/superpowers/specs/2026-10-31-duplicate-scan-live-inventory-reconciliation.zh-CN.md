# 重复扫描中的线上对象变化对账设计

## 意图

重复内容扫描按本地全盘缓存生成候选，但每个候选开始哈希和完成哈希时都会向百度读取当前文件元数据。若文件在两次全盘扫描之间被改名、移动、替换或修改，当前流程会将整轮重复扫描标记失败；除 MD5 变化外，不会把成功读取到的新身份反映到库存缓存。用户此前已明确：发生本地缓存与远端结果冲突时以线上结果为准，并更新本地缓存。

## 目标与五项独立用户结果

1. **线上身份变化同步到库存**：成功取得同一 `fs_id` 的当前元数据后，事务性更新文件路径、名称、父目录、大小、mtime、MD5 和百度观测 UTC；新旧父目录标为待刷新，移除旧 SHA-256。
2. **不完整对象响应安全暂停**：百度元数据接口未返回唯一匹配对象时，不据此删除库存或哈希；使旧父目录待刷新，清除活动哈希检查点并暂停当前扫描。
3. **保留可恢复扫描游标**：变化的候选不计为已完成、不推进 `next_fs_id`，不把半成品摘要记为已验证；受影响缓存重新完整后，继续时按最新候选重新估算总文件数/字节并从当前候选重试。
4. **缓存派生结果同步失效**：受影响父目录及其子树状态、账号级大小代次与候选 SHA 在同一事务更新，缓存目录浏览、目录大小与重复预览不再把旧身份显示为完整数据。
5. **保存可审计的变化证据并指导恢复**：追加事件保存本机记录 UTC、百度观测 UTC、旧/新对象快照及待刷新的父目录；网页明确显示暂停原因和刷新路径，不出现自动删除或自动重发入口。

## 非目标

- 不自动删除线上或本地对象；不依据 HTTP 错误码、空响应或权限失败推断对象已删除。
- 不自动启动目录刷新，也不发起除已有候选元数据/内容 GET 外的百度请求。
- 不改变未知远端写操作隔离策略，不启动真实账号大规模哈希扫描，不执行云端写入。
- 不声称完成百度 Range 或 NAS/SMB 实机验收。

## 方案

1. **保留失败关闭现状**：最少改动，但用户只能手动重新启动整轮扫描，成功读取到的新元数据仍不会进入本地缓存。
2. **对成功的线上元数据做事务性对账，目录待刷新时暂停扫描（采用）**：将百度成功返回的当前身份写入缓存并清除旧哈希；新旧父目录待刷新；失败/无唯一对象回执则保留库存、仅使原目录待刷新。扫描保留未完成候选，用户刷新受影响路径后可恢复。无需猜测 API 错误码，也不自动增加扫描请求。
3. **自动刷新受影响目录并继续**：交互更少，但自动引入额外百度分页请求，可能遭遇限流或在变更中得到不一致列表；不采用。

## 状态与时间语义

- `observed_at_utc` 只记录百度成功响应的观察时刻；`recorded_at_utc` 记录本机将观察提交到 SQLite 的时刻，两者各自保留。
- 不完整对象响应没有可用的百度对象快照，不伪造其观察时间；事件记录本机时间及原路径，并标记 `identity_unavailable`。
- 对账事务仅在缓存中的旧 `fs_id/path/parent/size/mtime/MD5` 与扫描候选仍一致时提交；若缓存已被其它操作改变则回滚并暂停，等待目录刷新。
- `next_fs_id` 和已处理文件/字节只代表完整校验并提交的候选；活动 SHA 检查点在身份变化时清除。
- 继续扫描仍要求账号级全盘扫描状态与根目录覆盖完整。恢复入口重新计算未完成候选总量；未完整刷新前拒绝继续。

## 验收

- Store 回归：路径/名称/大小/mtime/MD5 变化事务更新；SHA 清除；新旧父目录失效；大小 generation 增加；对象快照及本机/百度时间分开持久化；旧缓存身份或扫描队列冲突时不作部分提交。
- Store 回归：无唯一匹配对象响应只使原父目录失效，不删除原库存/哈希；检查点清除与扫描暂停及事件证据原子提交。
- Downloader 回归：哈希前和哈希后发生的身份变化都停止后续下载/入库，保留 `next_fs_id` 与已完成计数；更新缓存后恢复被完整刷新阻止，刷新完成后候选重新估算并从头核验当前对象。
- API/WebUI 回归：状态显示“远端对象已变化/待刷新”，事件展示旧新快照与两个 UTC 时间；HTML 样式路径按文本转义，无自动远端写入或自动刷新请求。
- 发布门槛：本批仅在 5 项独立用户结果分别具有回归证据且全仓 Go 测试、vet、WebUI/userscript、三平台构建和 ZIP/源码快照核验通过后发布一个 preview；未达到门槛时继续累计，不编号。
- 外部边界：真实账号只读健康检查可以单独进行；不执行云端写操作、大规模哈希扫描或 NAS/SMB 验收。
