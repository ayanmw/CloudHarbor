# 远端操作重启恢复时的缓存安全

## 背景

网盘变更在网络请求前先保存 `prepared`。进程重启后无法证明操作是否已发送，正确做法是转为 `unknown` 并隔离来源，不重发。然而云端变更也可能已生效；若本地全盘缓存仍保留 `complete`，网页会把旧目录内容和大小当成仍可信。

## 方案

采用 SQLite 内同一恢复事务：把所有遗留 `prepared` 记录转成 `unknown`、追加恢复事件，并将该操作可能影响的本地目录覆盖状态标为 `stale`，同时更新缓存 generation。保留原缓存行和内容哈希，不删除、不改写为推测的新状态。来源与目标路径、父目录及目录子树都按网盘路径规则处理；账号范围仅限操作记录中的账号指纹。

比较过两种处理方式：继续只隔离队列会保留可能过时的 `complete` 缓存；重启时调用百度核对会引入自动网络请求，且仍无法证明崩溃前操作的原子结果。采用本地事务失效方案，等待用户显式刷新缓存，不增加云端调用。

## 验收

- 进程重开后，遗留操作为 `unknown`；事件包含重启恢复原因、受影响的缓存路径和本机记录 UTC。
- 源/目标父目录和已缓存的受影响子目录覆盖状态同事务变为 `stale`；旧缓存条目、哈希不被删除或改写。
- 同一 SQLite 事务故障回滚时，不出现“操作 unknown 但缓存仍 complete”或部分目录失效。
- 其他账号的目录覆盖状态保持不变。
- 不发百度 API 请求，不自动重放，不释放原隔离。
- 仅本机 SQLite/mock 验证；真实百度和 NAS/SMB 验收另计。
