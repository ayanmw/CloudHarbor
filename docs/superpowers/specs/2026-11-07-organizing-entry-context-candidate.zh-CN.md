## 问题与现有基础

用户希望文件去重、目录分析方便解决同步冲突。当前比较、去重和冲突决策后端已经交付并有真实证据，不再重建算法或增加另一套删除策略。

源码核查：

- `CloudFilesWorkspace.vue` 有 `selectedEntries` 和已确认的目录/排序/分页状态，尚无从该列表进入目录分析或范围去重的入口。
- `DuplicatePreview.vue` 已接受 `directory` 查询参数，重复组已有“比较所在目录”；`DirectoryAnalysisWorkspace.vue` 已接受 `left`、`right`，不会自动生成报告。
- `CloudToolsNav.vue` 已有当前目录缓存入口及返回目录链接；`CloudCleanupWorkspace.vue` 没有把去重范围作为该返回链接的上下文传入。
- `cloud-files-route.ts` 已有 `readCloudFilesRoute` 和 `cloudFilesRouteURL`，能够规范化受支持的浏览状态；`validCloudSearchReturn` 仅用于缓存搜索返回，不能放宽其现有合同来承载所有工作台链接。

## 本批只做三个用户可见结果

1. **当前目录范围去重**：网盘文件页提供有边框、文字明确的“整理当前目录”入口，进入 `/cloud/cleanup?directory=...`，显示实际范围。只预填范围，用户明确读取预览；不自动扫描、选择或清理。
2. **选中两个目录比较**：选择恰好两个有效、不同且互不包含的目录后，提供“比较所选目录”。进入分析页并预填左右目录，仍由用户明确生成缓存比较报告。单文件、混合选择、相同目录或父子目录给出就近原因，不把无效选择转成全盘范围。
3. **返回原浏览位置**：由这些入口进入去重/比较页后，返回链接保留已提交目录、排序、混排、分页及缓存搜索条件。过期快照继续走原有一次恢复合同；不恢复删除勾选、未提交表单、执行确认或历史写请求。

这是一个内聚的前端工作流批次：复用已有 API，无数据库迁移，不修改上传、下载或同步状态机。跨页全选、保存去重选择、收藏、预览、分享、回收站及 API 搜索扩展不属于本批。

## 路由与交互合同

- 整理页和分析页使用一个可选的 `return_files` 参数承载规范化的站内网盘浏览 URL，最长 32768 字符；重复该参数、外站 URL、协议相对 URL、片段和嵌套 `return_files` 一律拒绝。
- 新增 `validCloudWorkspaceReturn(value: string): string`，接受 `/cloud/files` 或同路径查询，调用现有解析/序列化函数规范化，只保存浏览参数。未知动作参数不会成为执行指令；不改变已有搜索返回校验。
- 当前目录和选择必须来自成功读取的当前列表。列表读取、批次操作、401 或结果失效时禁用入口并解释原因。不能借用上次目录的条目构造新比较。
- 目录重叠按路径段判断，`/a` 与 `/ab` 不算包含；默认左右按绝对路径的 JavaScript 字符串顺序固定，不跟随列表排序或迟到响应换位。进入比较表单后仍可由用户明确修改目录。
- 缺省 `directory` 保留现有手工全范围入口；明确给出但无效/重复的范围不得静默退回 `/`。显示错误，需用户明确修改为有效范围后才能读预览。
- 直接打开 `/cloud/cleanup`、报告历史链接和同步来源分析保持原有导航。只有经过校验的明确返回上下文才替换返回入口。
- 选项可通过键盘访问，窄屏动作换行，长路径可换行；宽表格仍局部滚动。保留报告的历史观察时间和线上核对边界。

## 验收与规模边界

每个任务先有失败回归，再做最小实现；覆盖中文/长路径、父子与相似前缀、错误/401、失效列表、外站/嵌套返回、分页快照过期、离页迟到响应及 BFCache。

实际安装包复查：从自有目录进入限定预览；选择两个自有目录进入分析；在生成报告前后返回原位置。UI 不产生清理或同步执行。复用已有真实去重/目录比较证据，只有实现改变的链路才补真实验收，不重复全部上传/下载矩阵。

测试交付仍走既有同版/切版规则、完整前端与 Go/vet/三目标、ZIP/编译身份/受保护数据核对。下一版开始前先核对已有脏工作区，按明确授权归档项目内容及创建启动基线标签；不创建 worktree，不 push。

## 为什么保持这个范围

三个结果共用同一浏览状态和两类已有只读工作台，能消除复制路径、重新定位和重新选择的维护负担。后端决策及执行已具备，不需要把新的偏好持久化或更多网盘 API 一并纳入；这样也能独立验收和交付。
