# 大队列任务分页索引设计

## 意图与边界

管理页会每秒或每两秒请求任务分页。当前 `GetTaskPage` 每次遍历全部根任务与非根活动任务，重新计数并用有界堆选择排序窗口；大历史队列因此在翻页时重复扫描。目标是在名称、大小排序下复用稳定排序结果，并复用未变化的全局状态计数。

本次不改变任务排序、分页/API/WS 响应、队列持久化格式、历史保留、进度排序或下载调度语义。进度排序仍扫描任务，因为进度是频繁变化的排序键。索引按需建立，增加与历史任务数成正比的轻量 ID 切片内存。

## 方案

1. **按需名称/大小排序索引和状态摘要（采用）**：首次请求某个稳定排序时构建 `fs_id` 排序切片；之后根据 offset/limit 直接读取窗口。用独立版本号使任务集合/元数据变化失效排序索引，任务状态/集合变化失效全局计数摘要。收益覆盖定时刷新的稳定排序页与健康统计，新增内存约为每个已使用排序索引 8 字节/任务。进度排序继续走当前扫描路径。
2. **仅缓存状态计数**：减少 health 和页摘要遍历，但分页选窗仍对全部任务扫描，无法改善主要分页成本。
3. **持久化数据库或多排序物化视图**：可进一步减少启动与查询扫描，但需要存储迁移、事务/崩溃语义和历史兼容设计，超出本次可独立验证的增量。

采用方案 1，因为它直接处理常见 name/size 分页的重复全队列扫描，保持 API 和磁盘兼容，并把频繁变化的 progress 排序留在正确性优先的动态路径。

## 实现约束

- 排序键与现有 `taskCandidateComesBefore` 完全一致：name 使用路径（为空时文件名）的 `strings.ToLower` 升序并以 FsID 升序打破平局；size 降序并以 FsID 升序打破平局。
- 每个索引只保存排序后的 FsID，不保存 Task 副本；返回页时在既有锁下从当前 job/task 映射构造视图和操作能力。
- 新增/替换任务信息或活动任务进入列表时使排序索引失效；持久化 job 状态变更、活动 task 状态变更、新任务进入列表时使全局计数摘要失效。
- 版本失效使用原子计数，避免从 `taskMutex` 持有期间反向获取 scheduler 锁；读取与重建仍在现有 `queue.mu`、`taskMutex` 锁保护下。
- 索引未准备或版本不一致时重新构建；结果语义和进度排序的现有堆选择算法保持一致。

## 验收

- 测试 name/size 多页、平局、大小写与 FsID tie-breaker 和既有全量排序一致。
- 测试索引建立后任务新增/元数据替换会更新排序窗口；摘要建立后状态变更和非根 task 状态变化会更新计数。
- 测试调用方修改返回的 Counts 不会污染缓存。
- 10,000 条和 100,000 条历史基准分别记录首建索引、缓存命中和 progress 扫描时间及分配；报告冷热路径，不以单次测量承诺 NAS 提速。
- 全模块 Go test/vet/race、Node 测试、三平台发布构建及独立包 Linux 启动冒烟通过。
