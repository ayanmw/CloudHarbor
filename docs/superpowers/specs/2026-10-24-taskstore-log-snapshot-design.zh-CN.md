# 任务历史日志与快照设计

英文原文：[Task history journal and snapshot design](2026-10-24-taskstore-log-snapshot-design.md)。

## 目的

将目前每个根任务一个文件的历史存储改为顺序日志回放并定期生成快照，以降低 NAS 文件系统上的重启耗时。现有 v1 队列必须在不丢失任务历史、也不削弱源操作不确定状态保护的前提下迁移。下载器启动后仍会保留当前完整的内存任务映射；本方案优化启动时的文件操作和后续持久化开销，不降低常驻内存占用。

用户要求按优化计划持续改进，并阶段性提供可独立测试的版本。本文档提出一份供审阅的设计基线；在设计获批前，不授权实现新的磁盘格式。

## 目标

- 将启动时逐个枚举并打开每条任务记录，改为只打开数量有上限的快照文件和日志文件。
- 保留每个任务最近一次可靠落盘的完整 `queueJob` 状态、任务排序约定、任务查询行为，以及完整的已完成/失败历史。
- 保留预写顺序：`SourceState="sending"` 状态必须先可靠持久化并确认，之后才能发起云端改名/删除请求。
- 保留队列范围绑定、单写入者锁、私有文件权限、符号链接/重解析点防护、记录大小上限，以及遇到损坏时失败关闭的行为。
- 迁移现有由 `manifest.json` 和 `jobs/*.json` 组成的 v1 队列；完整 v2 快照可靠发布之前，不修改 v1 源记录。
- 入队操作日志、凭证、管理员密钥和下载模式设置继续保存在当前独立存储中。
- 增加基准测试和合成迁移/恢复测试；只有全部验证通过后才发布不可变预览包。

## 非目标

- 不改变任务生命周期、重试策略、源项改名/删除行为、不确定结果隔离策略或历史保留策略。
- 不减少完整的内存任务映射，不改变任务 API 的响应内容。
- 不引入 SQLite 或可在运行时配置的存储后端。
- 不根据本地 ext4/Windows 测试宣称 NAS 性能或断电安全保证。
- 不自动将已迁移的 v2 队列降级给旧版本程序。旧版本遇到 v2 清单时必须明确拒绝启动，不能读取过期的 v1 记录。

## 约束与当前证据

- v1 为每个任务保存一个 JSON 文件。`Save` 会写入并同步临时文件、原子重命名，再同步父目录。`SaveBatch` 会逐个同步临时记录、发布每个文件名，最后同步 `jobs` 目录。
- 正常任务生命周期会持久化新建的 `pending` 记录、开始工作前的 `downloading` 状态，以及完成/失败记录。重试、取消、认证等待和源操作状态也会持久化完整任务。
- 启动依赖 `LoadEachRaw` 的文件名顺序和严格校验。损坏记录、不安全路径、或发现第二个写入者时，程序会停止启动。
- 入队日志中处于 `sending` 的记录在重启后会转为 `unknown`；没有同步完成凭据时仍保持隔离。该日志不在本次改造范围内。
- 不选择 SQLite WAL，因为其官方文档说明 WAL 不适用于网络文件系统；NAS/SMB 的锁和同步行为也会因实现而异。本地基准不能替代目标 NAS 验收。

## 已评估的方案

1. **继续每个任务一个 JSON 文件。** 保留现有行为且无需承担迁移风险，但已知的大量小文件启动成本仍然存在。如果新格式无法满足耐久性测试，或目标 NAS 测量没有显示收益，则保留此方案。
2. **使用 SQLite。** 可提供事务和索引，但会引入数据库依赖，并带来网络文件系统锁与耐久性方面的顾虑。WAL 不适用于预期的 NAS 队列目录；回滚日志模式仍依赖 NAS 对锁的实现。
3. **使用仅追加任务日志并定期生成完整快照。** 可减少活跃文件数量、支持顺序回放，并可继续使用现有完整 JSON 任务记录作为每条事件的负载。该方案需要设计帧格式、校验和、检查点以及明确的 v1 迁移流程。推荐将其作为基线，因为它直接针对已测得的文件打开瓶颈，且不依赖 SQLite 在 NAS 上的锁语义。

## 建议的格式与写入语义

- 根清单 v2 绑定队列范围，并指定一个任务存储目录。该目录包含代次清单、一个不可变快照和一个当前活动日志。入队与凭证旁路文件仍作为同级文件保留，沿用当前 API。
- 快照按当前 v1 文件名顺序保存每个 `FsID` 最近一条完整 `queueJob` 记录，以保持 `LoadEach` 的回调顺序约定。
- 日志帧包含单调递增的序号、`FsID`、负载长度、校验和，以及完整序列化的 `queueJob`。单条 `Save` 帧必须完整写入并 `Sync` 后才能返回成功。`SaveBatch` 先校验所有输入，再追加批次并同步后才返回成功；发生错误时，调度器停止运行，云端源项仍可供后续扫描恢复，行为与当前一致。
- 回放从快照序号开始，并应用所有更新的日志帧。重复/乱序序号、无效 ID、超长帧、无效 JSON 或校验和错误都必须失败关闭。
- 任意不完整的尾部帧都必须导致启动失败，不能静默忽略或截断。撕裂的尾部可能包含 `sending` 状态变更，而底层文件系统可能并未可靠完成该次同步；若静默丢弃，就可能导致后续重复执行云端修改。日志必须原样保留以供诊断。
- 检查点操作持有存储写锁。先写入并同步新的完整快照，再创建并同步新的空日志代次，然后原子切换代次清单并同步其目录，最后才允许清理旧代次。若在清单切换前崩溃，旧代次仍是权威数据；若切换后崩溃，新快照和日志均已就绪。
- 保留现有单进程写入锁及平台专用的安全文件打开规则。新文件使用仅所有者可访问的权限。在支持目录同步的平台上，同步失败仍应报错；不支持的平台必须如实报告，不能声称数据已可靠落盘。

## v1 迁移与恢复

1. 打开并校验现有 v1 清单及每条旧任务记录，使用当前已加固的加载器。保持所有源文件不变。
2. 根据全部记录构造暂存的 v2 快照，同步快照和暂存目录，然后原子发布 v2 存储目录并同步其父目录。
3. 只有暂存存储完整且可重新打开后，才原子替换根清单为 v2。在开始替换清单前，v1 始终是权威数据；此之前发生错误时，只能删除不完整的暂存目录，并继续使用 v1。如果清单写入/重命名/目录同步报告错误，实际持久化结果属于不确定：必须关闭存储并让启动失败，且不得执行云端修改；保留两代数据供下次启动检查。同一进程中不得在切换结果不确定后继续使用 v1 模式。
4. 切换后 v2 成为权威数据。若 v2 缺失或损坏，不得静默回退到过期的 v1 记录。直到 v2 已重新打开并校验成功后，才可通过可在重启后继续的清理流程删除旧记录。若清理中断，v2 仍然有效，下次继续清理。
5. 说明迁移期间的临时峰值磁盘占用和禁止自动降级的规则。程序日志和测试说明必须明确呈现迁移结果。

## 验证与成功标准

- 单元测试覆盖帧编码、校验和/长度限制、序号校验、顺序、批量追加、同步错误、正确回放、不完整尾帧失败关闭、中段日志损坏，以及清单切换前后发生检查点崩溃的情况。
- 迁移测试从真实 v1 夹具开始，确认迁移后每个 `FsID` 的负载及顺序完全等价；在每个发布边界注入失败，并证明切换前 v1 源数据仍可恢复。
- 下载器回归测试证明：发送源 HTTP 请求前 `sending` 已可靠持久化；重启仍会把未决 `sending` 转为 `unknown`；任何错误路径都不会自动重发云端操作。
- 使用相同 Go 工具链和夹具，在 Windows 与 WSL ext4 上比较 10k/100k 合成队列启动，报告中位数、分配/堆数据、迁移峰值磁盘占用，以及冷/热启动结果。没有目标硬件时不得宣称 NAS 性能收益。
- 运行 Windows 测试/vet、Go 1.22.2 WSL race/vet、Node UI 测试、Windows AMD64/Linux AMD64/Linux ARM64 构建、不可变归档 payload 哈希检查，以及 Linux AMD64 包内冒烟测试。
- 只有所有测试通过、现有 v1 夹具无损迁移、故障注入证明提交前旧队列仍可用，并且包中记录了降级/损坏行为时，才算预览版成功。

## 留给实现阶段的决策

- 根据日志增长测量选择初始检查点阈值，不增加用户配置项。
- 从 Go 标准库选择紧凑、有版本号的二进制帧格式及校验和实现。
- 在现有存储生命周期允许的范围内，使迁移、检查点和旧数据清理有界且可取消。
