# 全盘扫描历史指定轮次对比设计

## 意图

在已自动展示“与上一轮完成扫描对比”之外，允许用户从历史中任意挑选两轮完成扫描进行定向比较。例如对比某次局部修复前后的全盘快照。结果只依据两行不可变 SQLite 历史数据，不使用实时缓存，不增加百度请求。

## 目标

- 历史每条完成记录可选；当前页面保留最多两条选择，跨筛选结果分页继续有效，切换账号/页面刷新会丢弃选择（单浏览器会话状态）。
- 对比时按 sequence 自动识别前序和后序，不依赖用户点击顺序。
- 对比覆盖状态、未完整目录数和九类原因计数；显示两轮 run ID、sequence、覆盖观察 UTC 与绝对快照。
- 两轮都必须是完成状态且 ID 不同。覆盖快照缺失时不计算摘要差值；原因快照缺失只禁用原因差值。
- 明确点击后可导出包含两轮快照与差值的脱敏 JSON；不发送新的 API 请求。

## 非目标

- 不新增 SQLite schema、API、百度请求或远端操作。
- 不跨页面/浏览器会话持久化选择，不把选择保存在 SQLite。
- 不改变 `.142` 自动相邻扫描比较语义。

## 方案

1. 浏览器从现有分页历史 API 已返回的不可变扫描摘要中保留最多两条用户选中记录，并在本机计算定向对比和 JSON 导出。推荐此方案：无新增后端/SQLite复杂度、无需重读历史；全部证据来自账号隔离的已认证历史页。限制是刷新页面后须重新选择。
2. 新增服务端比较 API，按两个 run ID 同一 SQLite 快照重读并生成导出。更适合长期链接/分享，但增加 API/Store 接口、校验和测试面，而记录本身已经是不可变快照。

采用方案 1。用户需要的是交互式本地历史核查；现有历史 API 已提供足够摘要，选择跨分页由页面内 Map 保存即可。

## 安全与证据规则

- 页面内选择以 `run_id` 为键，数据源只来自当前登录账号的已认证历史响应；导出明确列出来源为 SQLite 历史摘要，不含账号指纹。
- 仅两个 `status=complete` 且 ID 不同的运行可比较；如果同一 run 重复选中不允许当作两条记录。
- 按 sequence 升序排序。差值统一为后序减前序；NULL 不转换为零。
- 完整覆盖比较要求两轮均有 coverage status、未完整目录数及 coverage observed UTC。任一缺失即提供固定不可比较原因。
- 原因差值要求两轮 `coverage_reasons` 都存在；原始原因计数保留、计数可重叠。
- 下载只在用户显式点击时进行；名称不包含云端路径或凭证。

## 验收

1. 两页选择结果保留且最多两条；取消/清除其中任一选择能重算按钮状态。
2. 选择顺序反向仍以 sequence 识别前后，差值符号正确。
3. 非完成和同一轮选择均被阻止；缺失历史摘要与缺失原因分别呈现。
4. 比较显示双方运行标识、覆盖状态、未完整目录数、原因变化和两轮 UTC；转义不可信 ID/字段。
5. JSON 下载必须由显式点击触发，含两轮及比较结果、不含 account_fingerprint；过程不新增 API 请求。
6. WebUI 自动化覆盖跨页、取消、排序、NULL 和导出；全仓及 `.143` 三平台发布门禁通过。

## 实现边界

沿用 `internal/webui/index_cloud.html` 的历史列表 fetch、现有文案转义和 download pattern；只改 UI 与 Node WebUI 测试及文档。没有真实历史时用 mock 验证行为，真实账号仅只读启动。
