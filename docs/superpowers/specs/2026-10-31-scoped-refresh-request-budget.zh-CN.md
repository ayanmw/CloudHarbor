# 指定目录刷新请求预算

## 目标

为用户手动启动的指定目录及后代目录缓存刷新提供可选的百度目录列表请求上限。默认 0 表示不限，保持现有行为；设置上限后，程序不得因错误重试、暂停或进程重启而超过累计额度。额度用尽时保留有效 SQLite 检查点和旧缓存，不把未完成目录发布为完整。

## 方案与取舍

1. **对每个目录完整执行第二遍核对**：额外请求约等于首遍，且第二遍也不是远端原子快照；不采用。
2. **给现有局部刷新增加可选、持久化的列表请求预算**：复用选定目录范围、低频分页和检查点；每次向百度发列表 GET 前先在 SQLite 耐久预留额度，避免重启后重用已消费额度。额度耗尽后显示暂停状态，用户可追加额度继续。同一方向上改动 API、SQLite 与页面较多，但能准确约束累计请求；采用此方案。
3. **只在内存中限制单次进程的请求数**：实现简单，但重启即可重置额度并突破总上限；不采用。

## 用户行为

- 仅适用于网页手动启动的指定目录/子树刷新，不限制自动队列、完整网盘扫描或实时浏览。
- 新刷新可填写 0（不限）或 1..100000 次列表请求额度；未填写按 0 处理，保持兼容。
- 每次列表 GET 前，以事务递增 `requests_used`。网络失败、服务端限流和后续重试均消耗一次；进程在请求前后崩溃也不会让已预留额度退还。
- 请求预算字段和已用数量随刷新检查点跨重启持久化。额度用尽但仍有目录待扫时，运行状态进入 `paused` / `request_budget_reached`，保存当前 offset、边界、队列和已发布旧缓存；不发布 staging，不把缓存覆盖状态标记 complete。
- 恢复未耗尽额度的暂停任务可输入 0 使用剩余额度；额度已耗尽时，必须由用户提供 1..100000 的追加量。原不限额任务若用户在恢复时填写额度，则从已预留请求数之后开始设置有限额度。额度追加与恢复事件、额度状态同事务持久化。
- 页面与历史事件区分 `pages_processed`（成功提交页）和 `requests_used`（请求前已耐久预留次数），展示额度、消耗和暂停原因。额度不是请求速率限制；现有 pacer 与 Retry-After 退避继续生效。

## 持久化与兼容

- SQLite schema 27→28：局部刷新状态新增累计额度与已预留请求数；事件行追加额度快照，事件数据与状态更新同事务写入。
- 旧状态迁移为无限额度（0），已用请求计数从 0 开始，不改变既有扫描进度或缓存。
- 对已耗尽额度的检查、额度追加、请求预留和状态迁移均按 `account_fingerprint + run_id` 条件更新，避免跨账号或旧 worker 串改状态。
- 请求预留成功后即视为额度消耗，即使进程在 HTTP 发出前崩溃；这可能少用一次额度，但不会超额。

## 非目标

- 不为默认全盘扫描增加第二遍或额外请求。
- 不将预算耗尽视为完整、成功或可直接发布的目录快照。
- 不自动增加额度、自动继续额度耗尽的任务或修改用户配置的刷新范围。
- 不声称预算解决百度偏移分页的原子快照限制。

## 验收

- SQLite 回归验证 27→28 迁移保留刷新检查点并默认为无限额度；额度预留跨关闭/重开仍累加，达到上限后拒绝预留，额度追加和事件快照原子提交。
- Downloader mock 验证达到 N 次请求后最多只发 N 个目录列表 GET；错误/Retry-After 重试、暂停/恢复与强制进程重开均不会超额；预算耗尽保持当前目录 incomplete、未发布缓存不变。
- Intake API 验证单一额度参数的范围与缺省兼容；初始 run 的值表示总额度，同范围恢复的值表示追加量（不限额检查点则从当前已用数起设置剩余额度）；额度耗尽且未追加时不恢复。
- WebUI 验证上限输入、预算剩余/不限展示、耗尽提示、明确追加后才继续，以及旧缓存/分页检查点保留提示。
- 全仓 Go 测试、`go vet`、WebUI/userscript、三平台包检查和 SQLite 迁移回归通过。
- 本项只计下一批一条候选用户结果；未达到五项前不编号、不打包。此候选目前只做本机 mock/SQLite 验证，不以此作为真实百度账户限流验收。
