# 本地目录迁移历史检索设计

## 意图

迁移记录增加后，管理员可以按当前阶段筛选，或通过源/目标路径关键词定位记录，再沿用已有的按 ID 证据导出。该功能只查询本地 SQLite，不触碰迁移目录或百度网盘。

## 目标与范围

- 在迁移历史 API 增加可选 `status` 和 `q` 参数。`status` 仅接受 `running`、`failed`、`completed`；`q` 去除首尾空白后按字面子串匹配源路径或目标路径，最多 256 字节。
- `%`、`_` 和反斜线在关键词中作为普通字符匹配，不解释成 SQL LIKE 通配符。
- 状态、关键词、总数和分页条目在同一只读 SQLite 快照内计算；排序继续使用 `started_at_utc DESC, migration_id DESC`，每页最多 50 条。
- 页面提供状态选择、关键词输入、明确的搜索/清除操作；更改筛选后回到第一页，翻页和刷新保留筛选。旧请求不能覆盖当前筛选的结果。
- 选中记录导出继续调用 ID 专属接口，任何过滤条件都不能把导出重定向到最近一次迁移。

## 不做的事

- 不添加重试、恢复、删除或修改迁移记录的入口。
- 不搜索事件证据内容，不扫描本地文件系统，不访问百度 API。
- 不新增 SQLite schema、依赖或后台任务。

## 方案比较

1. **SQLite 服务端筛选（采用）**：过滤、总数与分页在一份只读快照中完成；内存和返回条目有界，并保持稳定排序。
2. **只筛当前页面**：改动较小，但用户会误以为其他页没有匹配项，也无法正确计算总数，因此不采用。
3. **浏览器先拉取全部历史再筛选**：接口和 UI 简单，但随历史增长而无界占用内存和网络，也无法满足有界读取，因此不采用。

由实施者沿用项目现有的参数化 SQL 与关键词转义方式；不引入新索引，迁移记录规模与既有查询足以支持此功能，若之后有性能证据再单独评估。

## 验收

- Store 覆盖每种状态、路径匹配、组合过滤、字面 `%/_/反斜线`、空结果、稳定分页和错误页参数；过滤总数与条目在同一快照查询。
- API 覆盖合法/非法状态、关键词长度/UTF-8、分页和保留的 next offset；无效输入返回 400，内部错误不泄漏。
- WebUI 覆盖筛选状态保持、换筛选回到第一页、筛选翻页、清除筛选、迟到响应忽略、按记录 ID 导出。
- 不产生任何百度 API 请求、本地路径 IO 或迁移状态变更。
- 全仓 Go 测试、vet、WebUI/userscript、Windows AMD64/Linux AMD64/Linux ARM64 构建、ZIP 清单与敏感数据排除通过。
