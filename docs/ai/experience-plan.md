# 阶段 D：入队与任务管理体验

目标：无需手写任务 API 即可管理后台下载；从明确选定的网盘项目发起服务端入队，补齐原油猴脚本尚未实现的能力。沿用已授权的持续实施和独立测试版交付范围，不操作真实百度账号。

## 当前源码证据

- 原 `tampermonkey_baidupan_nas_queue.user.js` 仅打印 window.yunData.FILEINFO；其自身注释说明这不一定是选中项，没有实际移动请求，不能据按钮名称认定入队已实现。
- 已有管理认证覆盖所有页面/API/WS，并拒绝跨 Origin 请求。不能为方便油猴调用而放开管理入口来源，也不能将管理员密码、百度 Token 放进网页 URL 或第三方页面。
- 下载器取消/重试 API 已有认证、状态和源扫描校验；取消成功不代表 active worker 已排空。任务策略固定在入队时，与默认模式分离。
- Go fs_id 为 int64；浏览器 Number 对大于 2^53 的 ID 可能失真。界面操作必须使用精确十进制 task_id 字符串，不从旧数值字段拼 URL。

## D2：服务端入队（核心与 HTTP/UI 已实现）

沿用项目原意，将用户明确选择的云端项目移动到配置的 QUEUE_DIR，页面必须提前展示源路径、目标目录及移动后语义，用户点击后才提交。目标目录固定使用服务端配置，冲突失败，不覆盖、不自动改名。下载完成仍依各根任务固定 keep/delete 策略处理。

- [x] 实现受管理认证保护的列表/预检/提交入口；输入不接受下载链接、任意目标目录或客户端提供的 Token。页面显示固定目标、策略和逐项结果，需要明确勾选确认。
- [x] 核心严格绝对云路径与项目标识校验；拒绝根目录、队列本身、队列祖先/内部项目以及同批父子/同名目标等歧义输入；返回逐项结果。
- [x] 官方 API 移动请求使用无覆盖策略；严格单项结果，禁止重定向重放，不把异步受理当完成；异步与失败码同时存在时仍隔离。
- [x] 持久化 sending/unknown、不自动重发；cloud 读写锁协调扫描/源后处理，逐目标隔离在重启后保留。只读核对与同步目录完成凭据保护已实现。
- [x] 每批 1..20 项、路径/记录长度上限、认证 epoch/进程标识/2 分钟预检；持久化后再查认证并在真正发送前撤销。
- [x] API 客户端/真实磁盘测试覆盖冲突、部分失败、回复丢失、重启、隔离、重复提交；Move 另有实际本地 HTTP wire 契约测试。目录缺失完成凭据的崩溃反例先 RED 后修。
- [ ] 可靠异步任务完成查询：接口契约尚未证实，当前 unknown 目录无同步凭据持续隔离。
- [x] 用户决定暂不提供人工放行；从计划中排除人工覆盖凭据的入口，API 和页面回归覆盖无 release/force/acknowledge。
- [x] 实际本地 HTTP 入队、单次 Move、真实磁盘持久化与重启读回；两平台全模块 race/vet、Node 7 项、独立 review 通过。浏览器隔离夹具验证选择、预检、确认和 unknown 提示。

依据：仓库内旧 SDK `doc/baidu-go-sdk/openxpanapi/api_filemanager.go`；本轮另核对[百度官方 Go SDK 文件管理模型](https://github.com/baidu-netdisk/baidu-drive-sdk-go/blob/main/baidudriver/api/file_manager.go)，其声明 copy/move 项 path/dest/newname、ondup 策略和单项结果；没有把 SDK 声明等同于真实账号执行成功。百度文档页本轮无法直接读取，实施时以可读取的官方代码及本地契约测试为依据，真实调用独立验收。

异步查询复核：本轮读取的[百度官方网盘 MCP 文档](https://github.com/baidu-netdisk/mcp)列出 copy/delete/move/rename 在 `async=2` 时返回 `taskid`，但其公开工具目录与说明未描述任务状态查询工具或可据以完成源操作的状态语义。这不能证明底层 API 一定不存在查询接口；现有证据仍不足以凭 taskid 或路径可见性解除 unknown 隔离。

2026-10-28 交叉核对：百度网盘组织的 [bdpan-storage Skill](https://github.com/baidu-netdisk/bdpan-storage/blob/main/skills/baidu-drive/SKILL.md) 记载 `status=submitted` 及 `get-content-result <taskid>`，但该查询用于文件正文解析，不是 filemanager 的 copy/move/rename。其文件管理章节仍仅描述异步请求返回 `taskid`，未提供对应完成查询契约。因此它不能解除本项目的异步 Move 阻塞；继续隔离未知结果，不用不同业务类型的 task API 推断可互换。

2026-10-29 复核：当前官方 [Go SDK FileManagerResponse](https://github.com/baidu-netdisk/baidu-drive-sdk-go/blob/main/baidudriver/api/file_manager.go)仍只定义 `taskid` 响应字段及 async 取值，没有公开任务状态查询方法；其 [`bdpan-storage` 命令参考](https://github.com/baidu-netdisk/bdpan-storage/blob/main/skills/baidu-drive/reference/bdpan-commands.md)描述的 `status=submitted` / `task_id` 属于分享转存与分享下载工作流，另有正文解析任务查询，未声明适用于 xpan `filemanager` 移动。仓库内 [MoveFile](../../internal/baiduapi/move.go)固定请求 `async=0`；若响应仍返回 taskid 或运行中 errno，仍按 unknown 处理。现有公开证据因此仍不足以恢复这类源项；不借用其它任务域的查询能力，也不按目标路径出现推断完成。

2026-10-23 追加核查：百度官方 [Go SDK API 文档](https://pkg.go.dev/github.com/baidu-netdisk/baidu-drive-sdk-go/baidudriver/api)仍将 `taskid` 定义为异步文件管理响应字段，但公开的 `FileManagerService` 方法清单没有任务查询方法；其链接的官方 Move 文档本轮无法读取。搜索到的 `/api/taskquery` 用例来自网盘网页脚本，使用的是浏览器页面环境，未证明它属于 OAuth 开放平台契约，也未给出可由应用凭据调用的授权、状态终态或结果一致性保证。因此本工具继续将异步 Move 结果视为 unknown；不调用网页登录 Cookie 接口、不按目标路径出现推断完成，也不提供人工解除隔离。只有取得适用于当前 OAuth 应用的官方契约并能对终态和单项结果做验证后，才继续设计查询接线。

- [x] 进度排序对无活动传输的历史任务直接使用固定进度比率：已完成文件为 1，其他任务为 0，只对实时传输按需计算进度比率。与 v0.8.11 对照、WSL 100 次样本中，10,000/100,000 条任务的 100 项进度页约 449/12,468 μs 降至 368/10,983 μs，分配量不变；全任务扫描和有界堆排序仍为 O(n log(offset+limit))，最坏 O(n log n)。
- [x] 进度页缓存非下载中任务的排序 FsID，并按活动进度动态合并下载中任务；缓存由任务统计代次失效。100,000 条合成历史、WSL Go 1.22.2：热进度页约 11–17 μs/op、38,171 B/op、106 allocs/op（旧实现约 6.9–7.3 ms/op）；索引重建约 33–36 ms/op、约 3.24 MB 临时分配。热路径约快 400–650 倍；代价是任务状态/集合变化后首次进度页需全量排序。缓存仅存 ID，排序比较使用紧凑预计算键。持久化队列仍在启动时加载全部历史；不改变现有记录保留语义。
- [x] SQLite 任务投影、追加事件、v1 格式迁移和重启隔离已实现并经回归验证；中文版设计见 [任务历史 SQLite 存储设计](../superpowers/specs/2026-10-28-taskstore-sqlite-design.zh-CN.md)。

## D6：重启时历史记录加载内存

> 下列 JSON 文件枚举、打开和解码数据均为 SQLite 迁移前的 v1 历史基线；v0.8.23-preview.1 后启动从 SQLite 读取，当前格式与测量见本节末尾及 D11。

- [x] 队列恢复改为逐条读取、校验并重建任务，不再同时保留完整 `map[int64]json.RawMessage` 与运行期任务映射；`Store.Load()` 原接口保留。
- [x] 已完成/失败/待处理等非活动记录只保留在 scheduler 的持久化 job 映射中；`Downloader.tasks` 仅保存实时传输进度对象。状态统计直接读取 job，分页排序使用轻量候选项且仅为返回页构造任务视图。
- [x] 独立包内 Windows 程序从真实状态目录格式恢复 10,000 条合成完成任务；管理接口读回全局总数/完成数 10,000 和 10 项分页结果，匿名访问继续拒绝。
- [x] Linux 恢复每条任务文件时合并 symlink 检查与文件打开：使用 `O_NOFOLLOW` 单次打开并继续拒绝符号链接，省去每条记录单独 `Lstat`；非 Linux 沿用原安全检查。
- [x] 下载器恢复使用不重复预解析 JSON 的 `LoadEachRaw`，随后由现有 `json.Unmarshal` 完成语法和结构校验；旧 `LoadEach` 与 `Store.Load` 保持已校验契约。
- [x] 任务 `ServerFilename` 与 `Path` basename 相同时复用路径字符串存储；云端扫描元数据与已持久化任务完全相同时，合格队列索引复用任务元数据，避免扫描后同时驻留两份同值字符串。非 basename 名称和变更元数据不做替换。
- [x] 100,000 条合成任务扫描后的保留堆由基线约 51.19 MiB（536.8 B/任务）降至约 47.40 MiB（497.0 B/任务），约减少 7.4%；单次 WSL 基准，不代表目标 NAS 的绝对内存值。启动仍须逐文件打开/解码并保留完整根任务映射，未改变 JSON v1 格式与记录保留语义。
- [x] 后续将 `eligible` 索引从每项完整 `FileInfo` 改为指针：身份相同则指向持久化 job 内的 `Info`，只有扫描身份与仍活动/结果未知的旧任务冲突时才保留独立快照。v0.8.7 基线 100,000 任务扫描后约 51.19 MiB，当前约 36.84 MiB（386.3 B/任务），约减少 28%；单次 WSL 合成堆样本，不代表 NAS 绝对 RSS，身份比较仍逐字段精确。
- [x] Linux `LoadEachRaw` 现在先以 `O_NOFOLLOW|O_DIRECTORY` 打开 jobs 目录一次，保持目录文件描述符，并对已校验的 basename 用 `openat(...|O_NOFOLLOW)` 读取；按原文件名顺序排序。非 Linux 保留逐条安全检查和完整路径打开。避免每条记录重复解析 jobs 目录路径，同时固定读取目录身份。
- [x] WSL ext4 合成对照（3 次/样本）：100,000 条 `OpenDownloader` 约从 900 ms 降至 606 ms；10,000 条 `LoadEachRaw` 约从 33.3 ms 降至 28.5 ms。样本说明本地路径查找/文件打开有改进，不代表厂商 NAS、SMB 或其他挂载的性能。
- [x] `LoadEach` / `LoadEachRaw` 在回调返回后复用同一个最多 1 MiB 的记录缓冲区；回调中的 `RawMessage` 生命周期在 `LoadEachRaw` 文档中明确为仅限本次回调。v0.8.10 对照后，10,000 条 `LoadEachRaw` 的分配由约 8.02 MB 降至 2.90 MB，100,000 条恢复 `OpenDownloader` 由约 144.93 MB 降至 93.72 MB；这是临时分配下降，不等于恢复后常驻堆下降。
- [x] 修复 `Store.Load()` 对 `LoadEach` 复用缓冲区的不兼容：收集到 map 的每条 `RawMessage` 必须复制，否则所有值会在扫描后变为最后读取记录；多记录回归测试曾先失败（记录 1 读回 ID 3），修复后通过。
- [x] 恢复时将合法 mode/status 规范化到共享常量，避免 Go 1.22 `encoding/json` 为每条任务长期保留相同枚举字符串的独立副本；JSON v1 与查询值不变。WSL Go 1.22.2 100,000 条保留堆由 v0.8.14 的 323.4 B/任务（30.84 MiB）降至 307.3 B/任务（29.31 MiB），减少约 1.53 MiB/5.0%；当前三次 `OpenDownloader` 为 753.5/548.4/543.1 ms，运行波动明显，不据此宣称稳定提速；分配量基本不变。Go 1.27 默认 encoding/json 已共享重复字符串，不能替代最低版本验证。源状态原有合法性校验已足够，不额外规范化。
- [x] Windows AMD64 单次合成基准：10,000 条 `OpenDownloader` 约 5.60 s、310.2 B/任务；100,000 条约 122.34 s、304.1 B/任务（保留堆 29.00 MiB）。100,000 条基准端到端耗时约 291 s，包含任务文件夹具创建；这暴露出 Windows 大队列恢复延迟，但不能外推 Linux/NAS，下一步需分离枚举、文件打开和 JSON 解码成本。
- [x] Windows 逐条恢复不再先按路径 `Lstat` 再 `Open`：使用 `FILE_FLAG_OPEN_REPARSE_POINT` 打开路径一次，再由已打开句柄核对符号链接，减少重复路径查找并消除检查后替换链接的窗口。Windows 5 组单文件 A/B 中位数约 522 μs → 191 μs；10,000 条 `OpenDownloader` 3 次约 2.73–2.76 s，先前单次基线 4.58 s；意外额外测得的 100,000 条 3 次为 36.0/45.8/36.8 s，先前单次基线 122.34 s。大队列提升对照受 Windows I/O 波动影响，只作本机趋势，不外推 NAS。Windows 本机无创建符号链接权限，直接 symlink 测试跳过；Linux 保持 `openat|O_NOFOLLOW`，WSL 安全测试继续运行。
- [x] Windows `LoadEach` 使用最多 4 个固定 reader 并行读小记录，再按文件名顺序调用 visitor；每 worker 重用缓冲区，最多 4 条记录在途，不按队列长度创建 goroutine。10,000 条 taskstore 原始读取单样本约 2.61 s（1 worker）→ 1.32 s（4 workers）；同批 Windows `OpenDownloader` 样本约 1.41/1.64 s，提升小于原始读取且受 I/O 波动影响。WSL ext4 的 10,000 条原始读取约 32–35 ms（串行）与 39–41 ms（4 workers），故 Linux/其他平台默认串行，避免本地盘回退。WSL 串行 100,000 条 `OpenDownloader` 3 次为 610/617/634 ms；不代表 NAS/SMB，Linux NAS 并行收益仍须目标存储实测。
